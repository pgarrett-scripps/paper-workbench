# Paper Workbench team handoff

Snapshot: 18 November 2026. Start here for the current framework. The companion [paper repository](https://github.com/pgarrett-scripps/paper-workbench-paper) holds the manuscript, study evidence, figures, recovery records and publication priorities.

## Engine and app split

PeerReviewAgents runs the review. Version 0.9.0 replaced its Python orchestration with the `pra` Claude Code plugin, run headless by `peerreview review`. The debate, the six review modes, the three policies, `ReviewRequest`, `run_review` and the Codex provider are gone, with no shim. The 0.8 engine is frozen at the PeerReviewAgents `v0.8.0` release. Version 0.10.0 replaced per-finding placement with issues. The editor groups the findings into issues, and `review/issues.json` is the review that `REVIEW.md` renders from. Engine main after that replaced block ids with a line-based manuscript: `paper.md`, one document per supplement, `map.json` with the page and box of each piece, and `manifest.json`. A finding names its document, its line and its offsets. Engine main at e7c8b65 adds the Read stage: an import writes a draft, and the reader, slot `reader`, repairs equations and tables against the page images, describes each figure and seals the manuscript before any reviewer starts. Each map row says in `source` whether the converter or a model wrote it, and the viewer labels every piece a model wrote. Engine main at 5244583 marks every such line for the reviewer, records the lines each lost page became, makes `write_manuscript` name the model behind any model-written piece with `ai_model=`, refuses an unstamped manuscript and says in `read_run`'s `manuscript.state` whether a run's manuscript is absent, a draft or sealed. Engine main at 3f475ca lets the reader re-read any piece on a page it has viewed as several pieces, with `original.part` and `original.of`, cut debris out of prose without typing it, fold debris pieces into the piece they belong to under `original.absorbed`, and leave a note on the document in `ai_read.note`, which the viewer shows as that model's account. Engine main at 23cb205 writes `original.absorbed` on one part of a re-read only, the first part that is not prose, adds `scripted_read`, a public way to build a read manuscript with a script in place of the model, and counts in `ai_read.gone` the absorbed, withdrawn and merged pieces that are no longer in the manuscript. The reader fixture is built through `scripted_read`, and the viewer does not show `gone`. Engine main at 4aae006 always runs the reader on a PDF review and drops `--no-ai-read`, `PEERREVIEW_AI_READ` and `ai_read=` with no shim. It adds a code reviewer: `--code FOLDER_OR_URL` snapshots the paper's analysis code into `RUN/code/` and plans one more specialist, `spec-code`, whose findings have basis `code-checked` and carry `code_evidence`, the file, lines and text the server found in the snapshot. The viewer shows that file and those lines on the finding, the run panel says which code was reviewed, and a Word review copy names them in the comment. Engine main at e88914d plans no Read stage for a run opened over a manuscript that is already sealed: `ingest` returns `reader: null` and mints no reader claim code, and a reader claim on a sealed manuscript is refused in words. Engine main at 496b2fa leaves out of a code snapshot the run folder being written and every other PeerReviewAgents run folder under the code, each listed in `skipped` with its reason, and makes `review_arms()` public, one row per arm saying among other things whether it reviews code. A workspace review can now write its run inside the workspace, and the app hands a workspace's code only to an arm whose row says it reviews code. Engine main at cf5b787 snapshots a git folder from its tracked files only and counts in `source_cut` the program source files a cap left out, cutting data files first. It lists the code's data files in the manifest's `data` and fetches one only when a reviewer reads it, partly when it is large, and counts them in `data_listed`, `data_fetched`, `data_partial`, `data_refused` and `data_bytes`. A new `code-check` slot reads each finding that rests on how a number was computed, with its `assumed_method`, against the code, and writes what it found to `code_check` in `issues.json`. A finding it contradicts is thrown out of every issue. The viewer lists the data files fetched, counts the code check's verdicts and shows each thrown-out finding after the issues with the code that contradicts it, never as an open issue. A Word review copy comments it the same way, and a revision keeps it in the issue ledger as `thrown_out`. Engine main at a4bfe33 hands the code check on in `read_run`'s `code_check`, read from `issues.json` or, on a run that stopped before its review, from `review/code-checks.jsonl`, so the app opens no run file itself. A run whose only finding the code check threw out is now a finished, publishable review with no open issue, and the run panel says the code check threw it out. Every review is now a fresh panel that knows nothing of an earlier review. Engine main at 9c36283 removed `--prior-issues` and every issue field about an earlier round, with no shim, and the app reads none of them. A revision's issue ledger is what remembers an earlier issue, with the author's decision and note on it. Engine main at c033002 adds `peerreview check-fixes`, which reads a new draft against a problems file of problems a review already raised and gives each a verdict of `fixed`, `not-fixed` or `cannot-tell`, read back with `read_fix_check`. It raises nothing new. Engine main at 47c41c6 adds `scripted_fix_check`, a public way to write a fix check with a script in place of the model, and the app's fix check tests use it. `paper-workbench check-fixes` runs the check on a workspace's current draft and records each verdict in its issue ledger. Engine main at 4bd27b6 lists in `review_arms()` and `--arm` only the arms a review runs, so `fix-check` is no longer offered to `review`. `paper-workbench review` of a manuscript workspace, and `import-run` for a run folder, add the problems of a finished review of the current draft to its issue ledger through `read_run` and `problems_from_run`, and `decide` records the author's decision on each.

This repository is the workspace, viewer and revision app. It pins engine 0.10.0 and is tested against PeerReviewAgents main at commit 4bd27b6. It starts a review through the engine's public `review_main`, the entry `peerreview review` uses, a fix check through `check_fixes_main`, and reads the run folder with the engine's `read_run` and a fix check with `read_fix_check`. Make review changes in PeerReviewAgents, not here.

Engine 0.10.0 is not on PyPI yet. CI installs from PyPI, so it stays red at the install step until 0.10.0 is published.

## Get started

Accept collaborator access to the private repositories, then clone them into sibling directories. Install the engine before the app. Until 0.10.0 is on PyPI, install it from the PeerReviewAgents main branch, or with `python -m pip install -e ../PeerReviewAgents` from a checkout:

```bash
git clone https://github.com/pgarrett-scripps/paper-workbench.git
git clone https://github.com/pgarrett-scripps/paper-workbench-paper.git
cd paper-workbench
python3 -m venv .venv
. .venv/bin/activate
python -m pip install 'peerreviewagents @ git+https://github.com/pgarrett-scripps/PeerReviewAgents@main'
python -m pip install -e '.[documents,test]'
paper-workbench --help
python -m unittest discover -s tests -p 'test_*.py'
node tests/test_review_evidence_ui.js
```

Use Python 3.11 or newer. PDF import and page inspection also require Poppler. Optional document export needs the renderer for that export path. The paper repository has its own locked toolchain and setup guide. The framework's optional dependencies are not fully locked, so record installed versions when preparing a new experiment.

To inspect a manuscript without model inference:

```bash
paper-workbench import manuscript.pdf workspaces/example --xml manuscript.xml
paper-workbench verify workspaces/example
paper-workbench serve workspaces/example --port 38744
```

Replace the source filenames with your own files. Omit `--xml` for PDF-only input. Open `http://127.0.0.1:38744`. Existing localhost browser tabs on Ty's machine are not shared deployments.

## Current architecture

`paper-workbench review manuscript.pdf RUN` runs one review, exactly as `peerreview review` does. It takes `--reviewers N`, `--arm NAME` and the per-slot model options `--reviewer-models`, `--specialist-model`, `--editor-model` and `--recorder-model`, with `--citation-workers N` and `--citation-worker-model` for the citation workers, and the default arm is `full-two-track`. `--code FOLDER_OR_URL` gives the review the manuscript's analysis code, such as the paper repository or its `analysis/` folder, and an arm that `review_arms()` says reviews no code refuses it. A Paper Scaffold workspace folder can stand where the PDF does, as in `paper-workbench review . reviews/one` from inside it. The app then reviews the workspace's built `paper.pdf`, refused when its build record says it does not match the source, and hands the engine the repository the workspace is in as the code, unless `--code` or `--no-code` says otherwise. On an arm that reviews no code it reviews the paper alone and says so, and only a `--code` the author gave on such an arm is refused. The run folder can be inside the workspace, because the engine leaves run folders out of its code snapshot. The viewer has no way to start a review, so every review starts here. The run folder holds `RUN/manuscript`, the imported workspace, and `RUN/review`, with `protocol.json`, `progress.json`, `runtime.json`, `findings.jsonl`, `issues.json`, the `audit_<track>.md` specialist reports, the citation ledger in `citations/ledger.jsonl` and `REVIEW.md`. `paper-workbench serve RUN` shows it. A run the starter stopped early, from a token ceiling, a timeout, a rate limit or a session error, has no `protocol.json` or `issues.json`. The viewer still opens it and shows its status, its cause and the findings it recorded. See [the engine contract](docs/shared-core.md) for the fields the viewer reads.

The viewer shows one card and one author decision per issue. The required changes, major and moderate, come first in rank order, then the minor suggestions under their categories. Each card shows how many reviewers raised it and its member findings as evidence, each with its track, its basis, any escalation and the editor's ruling on it. Every member is marked on the manuscript text. A run that is not publishable says why above its comments. A run panel shows the verdict, the specialist reports, one line per agent with the model asked and the model ran, the citation ledger and the run limitations. Author decisions on a run are saved in `RUN/manuscript/decisions/run.json`, so the review folder stays as the run wrote it. Every review is a fresh panel, so a later review is a new run folder that opens with no decisions. A run folder from an engine before 0.10 is refused with a message to re-run it.

A revision's issue ledger keeps one row per problem under an id that never changes, such as `original:run:i03`, with the problem as first raised, the author's decision and a history of fix checks of later drafts. `paper-workbench review WORKSPACE RUN` on a manuscript workspace reviews its current draft's built PDF, with that draft's source as the code, and adds the problems of the finished review as new open rows such as `original:r1:i02`. `import-run WORKSPACE RUN` does the same for a run folder, refuses an unfinished run or a review of another PDF, and adds nothing the second time. Problems of a review of a later draft are new rows that match no earlier one. `decide WORKSPACE PROBLEM STATUS` records the author's decision on a problem raised on the current draft. Review, decide, check fixes and a fresh review now run from commands with no hand-written file. Revise does not yet: `revise` takes a review response file and `revision-loop` makes copyedits only, so no command yet makes the next draft from source the author edited. Its status, open, fixed, declined, thrown out or not applicable for a copyedit, is read from the row. `paper-workbench check-fixes WORKSPACE RUN` writes the open problems of the current draft to the engine's problems file, runs the engine's fix check on that draft's built PDF and records each verdict with `record_fix_checks`. A problem the check did not reach is recorded as not checked and taken again by the next check of that draft. A blocked or unreadable check changes nothing. The fix loop is review, decide, revise, check fixes, and a fresh review when you want new problems found, as the [README](README.md#fix-loop) says. [Shared core](docs/shared-core.md#the-issue-ledger) has the details.

The engine anchors every finding to an exact source quotation by document, line and offsets, and labels its basis. The viewer reads that span off the manuscript and never searches for the quote again. Author decisions and revision exports are distinct from scientific adjudication. Exact source linkage does not establish that a criticism is scientifically correct.

`experiments/` keeps the protocols and results of earlier studies. Their runners were deleted, and git history keeps them, as described in [experiments/README.md](experiments/README.md). Study code that used the 0.8 engine runs only against PeerReviewAgents `v0.8.0`. Read the paper handoff before interpreting study results.

## Next step

The app reads a run only through the engine's public `read_run`, so a renamed key in a run file is the engine's to absorb. The viewer still reads `read_run`'s result keys by name, and a rename there breaks it without an import error. The next engineering task is a versioned run-folder fixture shared by both repositories, so an engine change that breaks the viewer fails a test. Every engine import is a public name, and a test fails if a private one comes back.

## Execution and collaboration

Offline inspection and tests need no model login. Tests stub the engine review and never start one. New model runs require the operator's own signed-in Claude subscription session. Do not copy account credentials. The run records its token use in `runtime.json` and stops at its own token and wall-clock ceilings. How much a run may spend is the operator's own setting.

Use a new run folder for each new attempt. Do not overwrite frozen outputs or automatically rerun the full study as a setup check.

Develop on a branch and open a pull request. Pin the engine commit, the arm, the literature cutoff and the source inputs for new comparisons. The run's `protocol.json` records what a run was allowed to do. The benchmark owns datasets, grading and statistics.
