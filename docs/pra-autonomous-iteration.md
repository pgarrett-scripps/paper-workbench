# Bounded review iteration

The next development pass closes the ecology comparison that previously failed, checks whether debate adds useful information without losing supported concerns, and fixes concrete failures before broadening the sample.

## Current pass

- Preserve every earlier run and its outcome.
- Use the same ecology manuscript, scientific supplements, figures and frozen source packet for a fresh single review and a fresh investigator plus debate review.
- Give both conditions the same initial tools and total tool budget. Disclose the additional generation call used by PRA.
- Use one anonymous model assessment of the main reviews. Keep supported secondary candidates in the product, but do not silently add them to only one judged review.
- Make the judge select immutable source handles. Expand exact quotations in code, including separate references when support spans multiple manuscript blocks.
- Check useful additions, unsupported premises, disproportionate requests, retained candidate components, complete delivery and observed token cost.
- Make deterministic repairs and run regression checks before considering another live development comparison.

This is a repeat-paper development assessment. The manuscript and prior outputs have already informed repairs. Its result cannot be presented as held-out validation.

## Budget and model decisions

The planned comparison permits four model calls: one single review, one investigator, one debate and one judge. The launch threshold is 400,000 observed input and output tokens. This threshold is checked between calls and does not guarantee a hard total token ceiling. No paid credits or account resets are used.

The first local launch failed before the CLI initialized because its state files were read-only. The second launch reached the provider, which rejected Sol with a model-capacity error. The provider supplied no usage receipt for that rejection, so its usage remains unknown rather than being reported as zero.

The comparison was then explicitly pinned to Terra, which the user had previously approved. Both review conditions and the judge use Terra. No automatic model fallback was added to the runtime. Sol remains the default for ordinary reviews. The failed launches remain in separate run directories.

## What determines the next change

If debate drops a useful candidate, inspect the recorded component decisions and the source evidence before changing selection instructions. Preserve supported secondary concerns when the main review is full. Do not force an unsupported concern into the final review just to increase recall.

If the investigator misses a concern the single reviewer finds, inspect whether the needed evidence was supplied, retrieved and examined. Add a targeted evidence operation or design-specific check only when the failure warrants it.

If a criticism is contradicted by accessible evidence, tighten the corresponding verification step. If evidence is missing, ask a consequential clarification or mark the issue unresolved.

If both reviews are similar, retain the result as a tie. Do not keep sampling until PRA wins. A workflow improvement must justify its extra cost through better supported findings, fewer misleading requests, better traceability or safer manuscript edits.

After this pass, the next broader evaluation should freeze the workflow and assess new papers across domains with independent expert spot checks. A single same-family model judge cannot establish superiority or replace scientific validation.
