# Engine contract

PeerReviewAgents 0.10.0 runs the review. Paper Workbench starts one and reads the run folder it writes. This page lists what the app depends on, so an engine change that breaks the app can be found before it ships. The app is tested against PeerReviewAgents main at commit cf5b787.

## Ownership

The engine owns ingest, source integrity, the line-based manuscript and its writer, the review plugin and its agents, tool access, the finding ledger, the issues document and the run reports. The app owns manuscript presentation, author decisions, revision workflows and exports. The benchmark owns datasets, hidden answer keys, candidate selection, controlled conditions, anonymous judging, statistics and rankings.

Neither answer keys nor human evaluation labels belong in a review. The benchmark must give the review a manuscript-only PDF and keep grading inputs outside the run folder. Engine outputs are review artifacts, not scores.

## What the app calls

Every review, report and run-reading call goes through the engine's public surface:

| Call | Used by | Model call |
| --- | --- | --- |
| `peerreviewagents.review_main(argv, prog='paper-workbench review')` | `paper-workbench review` | Yes |
| `peerreviewagents.review_parser(prog='paper-workbench review')` | `workspace_review.parser`, which adds the workspace and `--no-code` | No |
| `peerreviewagents.review_arms()` | `workspace_review`, to hand a workspace's code only to an arm that reviews code | No |
| `peerreviewagents.report_main(argv, prog='paper-workbench report')` | `paper-workbench report` | No |
| `peerreviewagents.read_run(path)` | `run_view.run_review` and `run_view.locate` | No |
| `peerreviewagents.read_citation_ledger(review, source_text=False)` | `run_view.citation_view` | No |
| `peerreviewagents.locate_run` and `NotARunFolder` | `run_view.locate` | No |
| `peerreviewagents.MANUSCRIPT_DIRECTORY` | `run_view.locate` | No |
| `peerreviewagents.import_paper(pdf, workspace, xml, ...)` | `paper-workbench import` | No |
| `peerreviewagents.write_manuscript(folder, documents, ..., ai_model=...)` | `paper-workbench import-scaffold` | No |
| `peerreviewagents.verify_workspace` and `export_draft` | `verify`, the viewer, revisions and exports | No |
| `peerreviewagents.cited_text(base, citation)` | `run_view.span_holds` | No |
| `peerreviewagents.citation_uses(base, references)` | the test that the citation fixture's uses are the engine's anchored rows | No |
| `peerreviewagents.MAIN_DOCUMENT` | Paper Scaffold import and port, table structure | No |

The app's `ENGINE_COMMANDS` must equal `peerreviewagents.CLI_COMMANDS`, and a test checks it, so an engine command added or renamed fails the app's tests until the app passes it on.

`paper-workbench review` hands its arguments to `review_main`, so a new engine option reaches the review and `paper-workbench review -h` names the program `paper-workbench review`. The per-slot model options `--reviewer-models`, `--specialist-model`, `--editor-model` and `--recorder-model` pass through this way, and a test checks that `review -h` lists them and that a blocked run's summary records them in `models_requested`. So do `--citation-workers N`, from 0 to 12 with a default of 4, and `--citation-worker-model`, which `PEERREVIEW_CITATION_WORKER_MODEL` also sets. A test checks that a blocked `full-two-track` run asks for the six specialist slots `spec-stats`, `spec-figures-tables`, `spec-methods-reporting`, `spec-citations`, `spec-numbers` and `spec-field` and one `cite-N` slot per worker, and that 13 workers is refused before the run folder is made. `--reader-model` sets the model of the Read stage, slot `reader`, which reads the page images before any reviewer starts. The Read stage always runs on a PDF review, and the engine has no switch to turn it off. A test checks that `review -h` lists `--reader-model` and not `--no-ai-read`, and that a blocked run records the reader in `models_requested`. `--code FOLDER_OR_URL` passes the paper's analysis code through the same way. The engine snapshots its text into `RUN/code/` and plans one more specialist, `spec-code`. A test checks that `review -h` lists it, that a blocked `draft-check` run given a folder asks for `spec-code`, and that a missing folder and an arm with no specialists are each refused with exit 2 and the engine's message on stderr, before any snapshot is written. Another runs every arm in `review_arms()` with a code folder and checks that each arm whose row says `code` asks for `spec-code` and every other arm is refused, so the row is what a review does. A Paper Scaffold workspace folder can stand where the PDF does, and `paper_workspace/workspace_review.py` turns it into the engine's arguments before `review_main` sees them. The PDF is the workspace's built `paper.pdf`, refused with exit 2 and nothing written when it is missing or when `.build-state/paper.pdf.json` says it does not match the source. The code is `--code` with the repository the workspace is in, unless the author gave `--code` or the app's own `--no-code`. On an arm whose `review_arms()` row says it reviews no code, the app hands over no code, because the author never asked for it, and its line on stderr says so and names the arms that review code. A `--code` the author gave on such an arm reaches the engine, which refuses it. A test checks both through the engine's starter with no `claude` on `PATH`. A run folder inside that code is fine, such as `reviews/r1` from inside the workspace, because the engine leaves the run being written and every other run folder out of its snapshot and lists each with its reason. A test checks that a blocked workspace run asks for `spec-code` and records the built PDF's digest, and a scripted round written inside a workspace, beside an earlier round, shows the engine's snapshot keeps its analysis code, leaves out its data, results, figures and `.env`, and copies no file of either run. `--prior-issues PATH` passes through the same way, and a test checks that `review -h` lists it. It is the only way to start a later round, because the viewer starts no review. It prints the run summary and exits 0 when the review completed, 1 when it was blocked and 2 when it never started or an argument was bad. The default arm is `full-two-track`. Without `claude` on `PATH`, the starter writes `startup.json` and a blocked `runtime.json` and launches nothing.

`paper-workbench report` hands its arguments to `report_main`, and `paper-workbench report -h` names the program `paper-workbench report`. It renders `REVIEW.md` and `REVIEW.txt` for any run, a stopped or startup-blocked one included, and exits 0. It prints JSON with `status`, `cause`, `findings`, `issues`, `required`, `suggestions`, `publishable`, `not_publishable_reasons`, `problems` and one key per report path. A path that is not a run, or a symlinked run file, is named on stderr with exit 1.

The smaller helpers come from the public `peerreviewagents.workspace`:

| Import | Used by |
| --- | --- |
| `digest`, `read_json`, `write_json` | decisions, revisions, exports and tests |
| `save_review`, `normalize_review` | revisions, `revise` and tests |
| `text_of` | table structure |

No module under `paper_workspace/` or `tests/` imports `peerreviewagents.engine`, `.plugin`, `.cli` or `.runs`, or imports one of those modules from `peerreviewagents`. There are two exceptions, both in tests. `tests/test_engine_rounds.py` imports the engine's plugin server to build two review rounds and a code run without a model, as the engine's own tests do, because the engine has no public way to. Each is opened over a manuscript that is already sealed, and the test checks that `ingest` returns `reader: null` and no reader claim code. `tests/fixtures/citations/generate.py` imports the engine's citation ledger module to write the ledger fixture, because the engine has no public ledger writer, and no test runs it. `PublicSurfaceTest` in `tests/test_engine_contract.py` fails if any other import comes back.

## The manuscript

The engine writes every manuscript as one base: `paper.md` and any supplement documents such as `S1.md`, with `map.json` and `manifest.json`. `verify_workspace` checks it and returns it. The app names a place in it by document and line, never by a block id.

1. A finding carries `document`, `line` and `end_line`, with `start` as an offset into `line` and `end` as one into `end_line`, and `evidence_lines` for the further lines it cites in its own document.
2. Each map row is a piece with its document, its lines, its kind, its section and the page and box it sits at in the PDF. A highlight on the page is that page and box plus the quote.
3. The viewer gets the base from `/api/paper` with each document as its list of lines and each piece as `document`, `lines`, `kind`, `section`, `page` and `bbox`. A link to a line in another document names that document.
4. `paper-workbench import-scaffold` cuts a Typst tree into pieces and writes them with `write_manuscript`, so a Scaffold manuscript is the same base a PDF import writes. A map row keeps only the fields the engine knows, so where each piece sits in the Typst source is kept beside it in `scaffold-spans.json`, one entry per map row, which the manifest digests.
5. `export_draft` returns `original_documents` and `proposed_documents`, each a document name to its text. A revision checks the draft it rebuilt against `proposed_documents`.
6. Each map row says whose text it is in `source`. `text` is the converter's. `ai-reconstructed` is a piece the reader read again from the page image, with the converter's reading kept in `original`. A piece the reader read again as several keeps the converter's whole reading in each, with `original.part` and `original.of` saying which part it is. A prose part of such a re-read is a slice of the converter's own characters that the engine cut where the reader said, so no model typed it. Debris the converter read as pieces of their own, folded into the piece they are part of, is kept on that piece under `original.absorbed`, one entry per piece with the converter's reading. In a re-read the engine writes it on one part only, the first part that is not prose, and the viewer shows it where it is written. `ai` is a piece the model wrote, such as a `figure-description` or text off a page the converter returned nothing from. `/api/paper` passes `source` and `original` on each piece and the manifest's `ai_read` beside them. The viewer labels every piece a model wrote and shows the reading it replaced under a closed toggle. A part of a re-read says which part it is of what the converter read as one piece, a cut prose part says every character in it is the converter's, and folded debris is listed under its own closed toggle. When a model read the pages it names `ai_read.reader_model` and says which page each piece was read from. `ai_read.note` is the reader's own account of the document, written when the read is sealed with its whitespace folded to single spaces. The viewer shows it as written above the manuscript as a note from that model, not the authors' text and not a review finding. `read_run`'s `manuscript.note` carries the same note, and the viewer takes it from the manifest so a workspace and a run show it the same way. The viewer does not read `known_gaps`, `ai_read.actions` or `ai_read.gone`, the count of absorbed, withdrawn and merged pieces no longer in the manuscript, because it shows no reader counts. Each page in `ai_read.lost_pages` is named above the manuscript and linked to the first of the lines its `added` entries name, and a piece inside those lines says it came from a page the converter returned no text from. When no page was read, it names `ai_read.ai_model`, the model the writer named, and says there is no page image to compare the piece with.
7. `paper-workbench import` calls `import_paper`, which seals the converter's pieces with no reader. The manifest then says the paper was not AI-read, and a PDF with a page the converter returned no text from is refused by that page. `port-scaffold` keeps each row's `source` and `original`, and keeps a figure description in the reading copy only, never in the Typst source. The port writes those pieces again with `write_manuscript`, which refuses a model's piece unless `ai_model=` names the model. The port records the source's reader, or the model its writer named, as `ai_model` in `pra-port.json`, and `import-scaffold` passes it on. The ported manifest then says `read` is false and names that model in `ai_model`, because no page image is read in a port.
8. `verify_workspace` refuses a manuscript whose manifest has no `schema_version`, and `serve` prints that refusal as a plain message.

## What the app reads from a run

`run_view.py` calls `read_run`, and `read_citation_ledger` for the citation rows. The section on the citation ledger below says how. The one run file it opens itself is the `issues.json` that `read_run` names in `reports.issues`, for its `code_check`, because `read_run` does not hand that key on. The section on the code check below says how. Nothing in the app writes to `RUN/review`. `read_run` refuses a symlink anywhere under the review folder, and the app shows that refusal as a plain error. It names any file it could not read in full in `problems`, and the run panel shows each one.

| `read_run` key | What the viewer does with it |
| --- | --- |
| `issues` | one card per issue. Required changes in rank order, then suggestions by category, then the closed issues |
| `findings` | the ledger. Each issue member is joined to its row by `finding_uid`, and a finding no issue holds is a card of its own, unless the code check threw it out |
| `findings_source` | `issues`, `ledger` or `none`, for the count line and the summary of a run that has not written its issues |
| `issues_source` | the run panel line saying whether the editor or the server wrote the issues |
| `prior_round` | the run panel line with the prior file, the issues carried and this round's tally by status, and whether cards show their status |
| `manuscript.sealed`, `manuscript.state` | whether the run has lines to show. An unsealed `draft` is a run whose Read stage started and never sealed, and `absent` is one that stopped before the import. `serve` names which, with the run's status and cause |
| `identity.paper_id`, `identity.source_sha256`, the `fingerprint` of each finding and issue member | the check that the run reviewed this manuscript version. A fingerprint must be the one on the map row at its finding's line |
| `status`, `complete`, `cause`, `note`, `problems`, `publishable` | the run panel's status and warnings, and the summary of a run with no issues |
| `not_publishable_reasons` | one line per reason, above the comments, when `publishable` is false. A run with nothing to show says it has no review rather than looking empty |
| `summary`, `verdict`, `escalations`, `escalation_rulings`, `limitations`, `guard_status`, `counts` | the summary and the run panel |
| `identity.arm`, `identity.reviewers`, `identity.workflow_version` | the run panel |
| `counts.quarantined` | whether a `complete-without-findings` run had nothing raised or had everything held by the guard |
| `stages.missing`, `stages.none_found`, `runtime.tokens_total`, `runtime.wall_seconds` | the run facts |
| `agents` | one line per agent, with its tokens, tool calls and state, and the tasks in `labels` when an agent ran more than one |
| `agents[].assigned_model`, `agents[].model` | each agent line shows both, as "model asked" and "model ran". A `model` of `None` shows as "model ran not recorded" and is never filled from `assigned_model` |
| `identity.models_unverified` | a run panel note naming the slots with a model asked and no model ran, when the list is not empty |
| `reports.audits` | each specialist report, read as plain text up to 400,000 bytes |
| `agents[].role` | a `citation-worker` line says the worker writes no findings |
| `citations.enabled` | whether the run panel has a citation section. A run whose plan has no citations lane has none |
| `citations.ledger` | whether the run has a ledger. `None` on a planned lane means the run wrote no ledger, so there are no ledger counts, and the engine's problem line says so |
| `citations.counts` | one line for the references and one for the uses. `resolved`, `not_found`, `not_located`, `could_not_check` and `unresolved` each keep their own count and are never added together. Empty `counts` with a ledger means the ledger could not be read, and the panel shows no rows |
| `citations.complete`, `citations.problems` | a line saying the check did not finish, and each problem line once, in the citation section. The engine puts those lines in `problems` as well, and the run panel leaves them out there |
| `code` | the run panel's code line, shown only when `code.reviewed` is true, as `REVIEW.md` shows it. It names the source, a local folder by its own name and a URL whole, the commit and whether it had uncommitted changes, how many of `files_in_snapshot` a reviewer opened, `searches`, `files_skipped` and `truncated`, and lists `files_opened` under a closed toggle. A snapshot with `source_cut` above 0 is said not to be the whole of the code. When `data_listed` is above 0 the line counts `data_fetched` of `data_listed` data files, with `data_partial` and `data_refused`, and lists each data file a reviewer fetched with how much of it was read and the engine's `changed` note. `run_view` passes every key but `manifest`, and passes the fetched rows of `manifest.data` as `data`, each with `path`, `bytes`, `stored_bytes`, `partial` and `changed` |

The engine writes `protocol.json` and `manifest.json` only when the run finishes or is marked blocked. A run the starter stopped early, from a token ceiling, a timeout, a rate limit or a session error, has neither. The viewer still opens it with its status, its cause and the findings in the ledger. Each finding's `fingerprint` then pins the manuscript version. Its arm and reviewer count are empty, because `read_run` takes them only from `protocol.json` or the plan. A run blocked at startup or before its import, or stopped before the Read stage sealed its manuscript, has nothing to show. `read_run`'s `manuscript.state` says which, so `serve` names it with the status and cause and exits 1. The app never looks for the engine's draft file.

A run written before engine commit bfc8aae recorded no model asked per slot, so each of its agent lines shows "model asked not recorded" and its `models_unverified` is empty. A slot that ran a different model family than it was asked is in `problems` and `not_publishable_reasons`, and the run panel shows it there. A `cite-N` citation worker holds no review, so its mismatch is a `problems` line only and the run stays publishable.

Each issue keeps every `ISSUE_FIELDS` key: `id`, `name`, `severity`, `category`, `rank`, `statement`, `members`, `raised_by`, `rebuttal_document`, `rebuttal_line`, `rebuttal_quote`, `prior_id`, `prior_rank`, `status`, `status_reason`, `text_unchanged_reason`, `surviving_quotes` and `audits`. A member carries its quote and where the engine placed it: `document`, `line`, `end_line`, `start`, `end`, `anchor_text` and `fingerprint`. `run_view.issue_card` joins it to its ledger row by `finding_uid` for `comment`, the span, `placement`, `replacement`, `basis_reason`, `counterevidence`, `source_urls` and `code_evidence`. A finding the `spec-code` lane filed with code has basis `code-checked` and a `code_evidence` of `path`, `start_line`, `end_line`, `text` and `sha256`, which the server checked against the snapshot before it stored the finding. A finding with no code has no `code_evidence` key. The viewer shows the file, the line or lines and the code on the member, and a Word review copy names them in the comment. The lines are lines of the snapshot's copy of the file, which for a notebook is its cells. A data file is fetched only when a reviewer reads it, so code evidence can quote one, and the member then carries its `manifest.data` row as `code_data`, which says how much of the file the review read. `tests/test_engine_rounds.py` files one such finding through the engine's server and checks the row's keys and the card. It reads the span off this manuscript with `cited_text` and keeps it only while that text is still `anchor_text`. A span that no longer holds is unplaced and keeps its line, and the viewer never searches the line for the quote again. The card takes `document`, `line`, `end_line`, `start`, `end`, `anchor_text`, `quote` and `fingerprint` from its first anchored member, the page and box from the map row at that line, and `evidence` as each document and line its members cite, once. It is an edit only when its one member is an anchored edit with wording, so accepting it applies exactly that wording. The card's `rebuttal_document` is the issue's own, the supplement its `rebuttal_line` is in, or the main document when it is empty.

The viewer keys a card by its issue id. A finding no issue holds is keyed by its `finding_uid`. A card whose id is missing, malformed, repeated or shaped like a place number is numbered `run-N` by its place and takes no decision, because a decision keyed on a place could land on another card once the order changed. The card says so and asks for a re-run. A decision already saved under such a number is kept in the file and not applied to an export or a revision. A revision's issue ledger keeps the issue id and the issue's status in the round that raised it.

The engine carries an issue id from round to round, but decisions do not follow it. They are saved in each run folder's `manuscript/decisions/run.json`, so a later round's run folder opens with none. The viewer cannot show the prior round's decision beside an issue, because the engine records the prior round only as `prior_round.file`, a file name relative to the prior run (`issues.json`), with its digest, issue count and tally, and nothing that locates the prior run folder. Showing it needs the engine to record that folder.

Saved decisions that no longer match a card, such as keys from the per-finding shape before 0.10 or an issue this round does not hold, are counted once above the cards. The decisions file is left as it is.

The app reads only the `issues.json` that engine 0.10.0 writes. A review folder with `editor-package.json` and no `issues.json` is from an older engine, and the viewer refuses it with "This review was made by an older engine, re-run it." A 0.10 run whose editor failed has neither file and opens with its findings as not publishable. The engine stamps `issues.json` `review-issues-v4`. `read_run` counts any other stamp, `review-issues-v3` included, as a problem, so the run is not publishable and its findings show ungrouped. `run_view.check_issues` checks the type of every value the viewer reads from an issue and its members, and a run with a wrong one is refused in one message that names the issue and the field.

## The code check

On a run given code, the engine's `code-check` slot reads each finding that rests on how a number was computed, with the method the finding took the code to use in `assumed_method`, against the code. `issues.json` records what it found in `code_check`: `cap`, `checked`, `over_cap`, `counts` by verdict (`confirmed`, `contradicted` and `not-shown`) and one row per check in `checks`. A run given no code has `code_check` set to `null`. `read_run` does not hand the key on, so `run_view.code_check_of` reads it from the `issues.json` that `read_run` names. A run with no readable `issues.json`, or one stamped with a version the engine does not read, shows no code check, and `read_run` already names that file in `problems`. An `issues.json` with no `code_check` key is refused with a message to re-run the review, and a value of the wrong type is refused in one message that names it.

A `contradicted` finding is one the code check threw out: the code does not do what it said. The engine keeps it out of every issue and `REVIEW.md` lists it under "Thrown out: the code does not do what the finding said". It stays in the ledger, and the viewer never makes it a card of its own. The run panel counts the checks by verdict, with how many findings over the cap were left unchecked, and the viewer lists each thrown-out finding after every issue, under the same heading as `REVIEW.md`. Each one is marked as thrown out and not an open issue, with its title, slot, track and severity, the quoted passage linked to its line, the comment, what the finding took the code to do, the code that contradicts it and the check's note. It takes no decision and no author response, and a filter, which shows only some of the issues, hides it. A revision adds it to the issue ledger with `scientific_status` `thrown_out` and no wording decision, so a later draft still shows why it was dropped and never counts it as an open question. A Word review copy comments it as thrown out with the same facts, or lists it under "Findings the code check threw out" when its passage cannot be located. The engine reads a run whose only findings the code check threw out as one with no issues: `findings_source` is `ledger` and the run is not publishable, although its `issues.json` exists. The engine records each check in `review/code-checks.jsonl` as well, a file its integration guide does not describe, so the app reads only `issues.json`.

## The citation ledger

Engine commit 3686516 plans six specialist lanes, `stats`, `figures-tables`, `methods-reporting`, `citations`, `numbers` and `field`. The lane that checks the manuscript's numbers against each other is `numbers`, with slot `spec-numbers`, report `audit_numbers.md` and finding track `numbers`. The app keeps no other name for it. The citations lane fills `review/citations/ledger.jsonl`, an append-only table of the reference list and every in-text use, with `citations/lookups/` and `citations/stages.json` beside it, and the writers' lock files `rows.lock` and `stages.lock`. The app never lists that folder. Citation workers `cite-1` to `cite-N` judge each use against the source text the ledger fetched. They write no findings.

The panel takes its counts and problem lines from `read_run` and its rows from `read_citation_ledger`, which gives the last row for each `row_id`. It asks for the rows only when `read_run` could count the ledger. It calls the reader with `source_text=False`, so the fetched abstract and full text stay in the run folder and each reference row says only whether a worker had them. The panel never showed that text, and the passage a worker quoted is on the use row. The reader gives the rows in reading order, with the numbers in a `row_id` compared as numbers, so `ref:r2` comes before `ref:r10`. The panel keeps that order and only moves the uses a reader should check first to the top. Rows are at most 500 of each kind and each text at most 1,500 characters, so the page stays small whatever the ledger's size.

The run panel lists the references that need a second look and every in-text use, the ones a reader should check first at the top, at most 500 of each. A reference is found in an index, has a DOI the DOI resolver does not hold, has a title neither Crossref nor Europe PMC lists, could not be checked because the lookups did not answer, or was never looked up. The panel never turns a title it could not locate, or a lookup that did not answer, into a claim that a work does not exist. A use's sentence and marker are as the paper prints them, so a superscript citation has a bare-digit marker such as `3` and a bracketed one has `[3]`. The panel shows the marker as the row gives it and adds no brackets. The only derivation the panel reads is `marker-author-year-ambiguous`, which makes an unmatched use say it matches more than one entry. Every other derivation, the `reader-link` forms included, shows the same way. A use shows its sentence, the worker's verdict (supports, partly supports, does not support or cannot tell), the source passage the worker quoted and its note. Passages and notes came from the internet or from a model, so the panel shows them escaped as quoted text, cuts each at 1,500 characters and links only `https` URLs. The abstract a worker read stays in the run folder.

A ledger that is present and cannot be read gives one citation problem line that names `review/citations/ledger.jsonl` and why. The counts are empty, the panel shows that line and no rows, and the run stays publishable. A torn last line is counted in `unreadable_rows` and the rows before it stand.

A use row names its sentence by `document`, `line`, `end_line`, `start` and `end`, and its `row_id` is `use:<document>:<piece first line>:<sentence>:<reference>`. The panel links each use to its line.

`tests/fixtures/citations` holds a ledger that `generate.py` wrote through the engine's own ledger code, with canned lookups and no network, and its README says what each row is for. No test imports the engine's private ledger module.

`tests/fixtures/reader` holds what `/api/paper` serves for a manuscript the engine's Read stage wrote and for its Scaffold port. `generate.py` writes it through the engine's public `scripted_read`, with no model and no network, and `test_reader_fixture` builds it again and fails when it is out of date. The viewer test renders both, so every reader shape it checks is one the engine writes.

## Versioning

Pin the engine commit, the arm and the literature cutoff for any comparison. The run's `protocol.json` records what the run was allowed to do, including the plugin and engine provenance hashes. A change to the plugin's agents, tools or editor rules is a new condition, even when no Python signature changes.

The 0.8 engine, with `ReviewRequest`, `run_review`, presets, policies and the Codex transport, is frozen at the PeerReviewAgents `v0.8.0` release. Study code written against it runs only there.
